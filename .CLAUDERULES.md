# Comprehensive Claude Guardrails — IDE-LSP for MCP

This document summarizes the complete set of guardrails generated to enforce the `vscode-lsp-mcp-extension` project's architecture and coding standards.

## 📋 Files Created / Updated

### 1. `.clauderules` (root level)
**Location:** `.clauderules`  
**Purpose:** Definitive guardrails file. Authoritative over generic AI patterns.

**Contents:**
- **§1 Architectural Constraints** — Two-process model, smart routing, protocol integrity
- **§2 Coding Standards & Patterns** — TypeScript targets, new-tool templates, error handling, logging conventions
- **§3 Development Workflow** — LSP skills (coordinate systems, reusable helpers), test templates, hooks
- **§4 File Structure & Build** — Directory boundaries, esbuild dual-entry lock, package management rules

**Key Principles:**
- Server (`src/server/**`) is pure Node.js; no `import "vscode"` ever.
- Client (`src/client/**`) owns all VSCode LSP calls; cannot import from `src/server/**`.
- Every tool request flows: `MCP Client → Server (HTTP/SSE) → TaskManager → WebSocket → Window → TaskExecutor → BaseTool → vscode LSP → result`.
- Smart routing: every tool (except `listOpenProjects`) carries required `projectPath` arg, resolved via `ClientRegistry.findByProjectPath()`.

## 🚀 How to Use

### Before Committing

```bash
# Run all pre-commit checks
./.claude/hooks/run-all-checks.sh

# If all pass, proceed to type check, lint, test
pnpm run check-types && pnpm run lint

# Then run affected test suites
pnpm test-unit          # if changed server/client code
pnpm test-mcp           # if changed tools
pnpm test               # if changed extension UI

# Finally push
git push
```

### During Development

When adding a **new tool**:
1. Follow `.claude/rules/claude-dev-patterns.md` §2 (tool template)
2. Ensure `src/client/tools/NewTool.ts` extends `BaseTool`
3. Add schema to `src/server/MCPTools.ts`
4. Register in `src/client/TaskExecutor.ts`
5. **Run `.claude/hooks/run-all-checks.sh`** to validate

When adding a **new protocol message**:
1. Follow `.claude/rules/claude-dev-patterns.md` §3 (protocol template)
2. Define interface in `src/shared/protocol.ts`
3. Add switch cases in both `McpServer.ts` AND `ServerConnection.ts`
4. Add tests to `src/test/unit/protocol.test.ts`
5. **Run `.claude/hooks/run-all-checks.sh`** to validate (will check handler symmetry)

## 🎯 Key Guardrails at a Glance

| Guardrail | Enforcer | Fix If Violated |
|-----------|----------|-----------------|
| Server is pure Node.js (no vscode) | `pre-commit-clauderules-check.sh` rule 1 | Move LSP calls to `src/client/` |
| Client doesn't import server | `pre-commit-clauderules-check.sh` rule 2 | Extract shared code to `src/shared/` |
| esbuild preserves dual entries | `pre-commit-clauderules-check.sh` rule 3 | Restore `esbuild.js` to canonical config |
| Protocol messages have handlers | `pre-commit-protocol-check.sh` (existing) | Add switch case to both McpServer + ServerConnection |
| Tools follow BaseTool pattern | `.clauderules` §2 + code review | Use template in `.claude/rules/claude-dev-patterns.md` |
| Smart routing via projectPath | `.clauderules` §1 + code review | Ensure every tool has `projectPath` arg, uses `ClientRegistry.findByProjectPath()` |
| i18n bilingual coverage | `pre-commit-i18n-check.sh` (existing) | Add keys to both l10n files with same key |
| Tests for new tools/protocol | `pre-commit-test-check.sh` (existing) | Add test data + expected results under `src/test/testData/mcp/` |
